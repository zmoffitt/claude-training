# Insights: See How Your Team Uses Claude

<ReadTime minutes={3} />

Usage patterns inform what to standardize, what to retire, what to invest in. Two surfaces give you that signal.

## Team analytics

Who's using what, how often — and what it ships.

Admins and Owners on Team and Enterprise plans get the Claude Code analytics dashboard at `claude.ai/analytics/claude-code`. It shows daily active users and sessions, lines of code accepted, suggestion accept rate, and, with the GitHub app connected, which merged PRs contain Claude Code-assisted code. A leaderboard and CSV export cover every user. Console (API) organizations get a similar dashboard at `platform.claude.com/claude-code` with per-user spend instead of GitHub attribution.

> _Example:_ Identity Engineering shows 12% weekly active vs. 78% for the Cloud team. A 30-minute walkthrough on `mg-graph` patterns lifts them to 60% the following week. The signal got there before the survey would have.

## Personal insights

Where each engineer's sessions go wrong.

Run `/insights` in Claude Code. It reads your last 30 days of local session transcripts, nothing leaves the machine, and writes an HTML report: usage stats, tool breakdown, and a ranked list of **friction points** with examples — misunderstood intent, buggy first attempts, repeated corrections. It ends with rules you can paste into `CLAUDE.md`. Ask engineers to bring their top friction point to a team review; five people hitting the same one is a skill or a hook waiting to ship.

> _Example:_ Three engineers' reports show "re-explained the CI layout" as the top friction. Promoted to a `ci-failure-triage` skill and a `.claude/rules/ci.md`, distributed via the internal plugin marketplace. Time-to-PR on flaky-test fixes drops from days to hours.

## Cost

Tokens, model mix, quota burn.

Per-user token and usage-credit spend comes from the organization's spend report export, or from OpenTelemetry metrics if you run your own observability stack. Per session, `/usage` shows what the current conversation has cost. Helpful for budgeting; more helpful for spotting **the wrong model on the wrong job**.

> _Example:_ A weekly report task on Opus is costing 2× what it needs to. Same prompt on Sonnet produces functionally equivalent output. Switching saves the team's quota for the work that actually needs the bigger model.
