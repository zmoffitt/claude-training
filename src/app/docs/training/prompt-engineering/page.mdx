# Prompt Engineering

<ReadTime minutes={4} />

A prompt is a work order. The good ones say what, where, why, and what done looks like.

## Core principles

### Be specific

Vague in, vague out. "Fix the bug" and "make this better" get the average of better, because the model fills every gap you leave with the most average possible answer. Name the file, the symptom, and the fix you want, and paste the error verbatim. A stack trace is more specific than any paraphrase of it.

```prompt
Fix the TypeError in src/api/users.ts:42 where `user.email` is undefined
when the OAuth provider doesn't return an email field. Fall back to the
UPN. Add a test for the no-email case.
```

### Provide context

Include what the model cannot see. In Claude Code, the repo is visible; your intent, constraints, and history are not.

- **What** you're trying to accomplish
- **Where** in the codebase the change belongs. In Claude Code, type `@` and pick the file; the path lands in the prompt and Claude reads it first.
- **Why** the current behavior is wrong, and what must not change

Anything you'd repeat on every task belongs in <Term id="claude-md">`CLAUDE.md`</Term>, not in the prompt.

### Break down complex tasks

One request, one outcome. For anything with a design decision in it, ask for the analysis first, then the plan, then the change. In Claude Code, <Term id="plan-mode">plan mode</Term> does exactly this: Claude reads and proposes, you approve, then it executes.

### Say what done looks like

The fourth item in the work order, and the one most people skip. The single highest-leverage line you can add is a verification step: "then run the tests", "then compare against the original", "then spot-check five rows". The [Verification Pattern](/docs/training/claude-code/session-1/verification-pattern) page has the four forms.

### Rewind instead of correcting

When an attempt goes wrong, "no, not like that" leaves the failed attempt in context, and the next one is shaped by it. In Claude Code, `/rewind` to the message before it and re-ask with the detail that was missing. [Context & Session Management](/docs/training/claude-code/session-2/context-session-management) covers when to rewind, compact, or start fresh.

**The same rules in Copilot.** The comment above the function is the prompt, the signature and your open tabs are the context, and the check is you reading the body before you press `Tab`. [GitHub Copilot](/docs/training/github-copilot) has the rest.

## Prompt templates

Replace the brackets. Keep the shape.

### Bug fix

```prompt
In [file], [function] has a bug where [problem].
Expected: [what should happen].
Actual: [what happens].
Fix it without changing [constraint], then run [test command].
```

### New feature

```prompt
Add [feature] to [module].
It should [behavior].
Follow the pattern in [reference file].
Add tests next to the existing ones and run them.
```

### Code review

```prompt
Review [file or diff] for:
- Security issues (auth bypass, injection, secrets)
- Error handling gaps
- Adherence to the conventions in CLAUDE.md
Do not change anything. Report findings by severity and quote the line
each one points at.
```

### Refactoring

```prompt
Refactor [function/class] to [goal].
Keep the public API the same.
Run the existing tests before and after; they must still pass unchanged.
```

### Runbook or policy work

```prompt
Draft a runbook for [incident type] for the on-call engineer.
Use the escalation matrix in docs/escalation.md.
Each step is one action with a command and an expected result.
Cite the section of docs/escalation.md each step relies on, and flag
any step that needs a privileged role.
```

<Callout variant="info" title="What the sessions teach" align="left">
  Every template above ends with a check the model can run or you can read.
  That is the program's one rule for prompts: never ask for an output
  without asking for the evidence that it's right. Raise <Term id="effort">effort</Term>
  for the hard ones instead of writing longer prompts.
</Callout>
