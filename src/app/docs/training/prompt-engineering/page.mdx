# Prompt Engineering

<ReadTime minutes={4} />

A prompt is a work order. The good ones say what, where, why, and what done looks like.

## Core principles

### Be specific

Vague in, vague out. The model fills every gap you leave with the most average possible answer.

```prompt
Fix the bug
```

```prompt
Fix the TypeError in src/api/users.ts:42 where `user.email` is undefined
when the OAuth provider doesn't return an email field. Fall back to the
UPN. Add a test for the no-email case.
```

### Provide context

Include what the model cannot see. In Claude Code, the repo is visible; your intent, constraints, and history are not.

- **What** you're trying to accomplish
- **Where** in the codebase the change belongs
- **Why** the current behavior is wrong
- **How** you'll know it's fixed

Anything you'd repeat on every task belongs in <Term id="claude-md">`CLAUDE.md`</Term>, not in the prompt.

### Break down complex tasks

One request, one outcome. For anything with a design decision in it, ask for the analysis first, then the plan, then the change. In Claude Code, <Term id="plan-mode">plan mode</Term> does exactly this: Claude reads and proposes, you approve, then it executes.

### Say what done looks like

The single highest-leverage line you can add is a verification step: "then run the tests", "then compare against the original", "then spot-check five rows". The [Verification Pattern](/docs/training/claude-code/session-1/verification-pattern) page has the four forms.

## Prompt templates

Replace the brackets. Keep the shape.

### Bug fix

```prompt
In [file], [function] has a bug where [problem].
Expected: [what should happen].
Actual: [what happens].
Fix it without changing [constraint], then run [test command].
```

### New feature

```prompt
Add [feature] to [module].
It should [behavior].
Follow the pattern in [reference file].
Add tests next to the existing ones and run them.
```

### Code review

```prompt
Review [file or diff] for:
- Security issues (auth bypass, injection, secrets)
- Error handling gaps
- Adherence to the conventions in CLAUDE.md
Report findings by severity. Do not change anything.
```

### Refactoring

```prompt
Refactor [function/class] to [goal].
Keep the public API the same.
Run the existing tests before and after; they must still pass unchanged.
```

### Runbook or policy work

```prompt
Draft a runbook for [incident type] for the on-call engineer.
Use the escalation matrix in docs/escalation.md.
Each step is one action with a command and an expected result.
Flag any step that needs a privileged role.
```

<Callout variant="info" title="What the sessions teach" align="left">
  Every template above ends with a check the model can run or you can read.
  That is the program's one rule for prompts: never ask for an output
  without asking for the evidence that it's right. Raise <Term id="effort">effort</Term>
  for the hard ones instead of writing longer prompts.
</Callout>

## Anti-patterns to avoid

- **Vague requests** — "Make this better" produces the average of better
- **Too many goals at once** — one prompt, one outcome; chain the rest
- **No acceptance criteria** — if you can't say what done looks like, the model can't either
- **Restating the repo** — Claude Code can read it; tell it what it can't see
- **Correcting instead of rewinding** — "no, not like that" piles failed attempts into context; `/rewind` and re-ask
